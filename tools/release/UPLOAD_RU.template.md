# Что заливать на GitHub — @@VERSION@@

Всё готовое собрано в этой папке. Порядок обязателен: сначала файлы приложения на CDN, потом релиз.
`releases/latest` переключается в момент публикации, поэтому релиз, чей манифест ссылается на ещё
не выложенные файлы, ломает обновление у каждого, кто успеет до него дотянуться.

## 0. Один раз перед первым релизом

- Нужны `gh` (GitHub CLI, с выполненным `gh auth login`), `git` и `curl` — всё это есть в Git Bash.
- Все три скрипта запускаются из этой папки:

```bash
cd @@UPLOAD_DIR@@
```

## 1. Файлы приложения → CDN

```bash
./publish-step1-cdn.sh
```

Создаёт публичный репозиторий `@@CDN_REPO@@`, если его ещё нет, превращает `@@CDN_DIR@@`
в git-репозиторий (при первом запуске) и пушит его в `main`. Внутри — файлы приложения
(@@FILE_COUNT@@ шт., @@PAYLOAD_MB@@ МБ), `.gitattributes`, `README.md` и копия манифеста.

Скрипт локально выставляет `core.autocrlf=false`. Апдейтер сверяет SHA-256 именно тех байтов, которые
отдаёт GitHub, а при обычной для Windows настройке `core.autocrlf=true` git заменил бы CRLF на LF в
`.cfg` и `.properties` — и каждое обновление падало бы с «SHA-256 mismatch». По той же причине в этом
репозитории нельзя включать Git LFS: `raw.githubusercontent.com` отдал бы текстовый указатель LFS
вместо файла.

Для следующих релизов скрипт можно запускать здесь же — он коммитит текущее состояние `release/cdn`.
Если репозиторий склонирован в другом месте, замените в нём `app/` целиком (удалить старую папку,
скопировать новую), чтобы исчезнувшие файлы попали в коммит как удаления.

## 2. Проверка CDN — до публикации релиза

```bash
./verify-cdn.sh
```

Скачивает все @@FILE_COUNT@@ файла из `@@BASE_URL@@` и сверяет размер и SHA-256 с манифестом.
Ожидаемая последняя строка: `All @@FILE_COUNT@@ file(s) match the manifest byte for byte.`
Любой `FAIL` — публикацию отложить и разобраться. Свежий push доходит до `raw.githubusercontent.com`
за считаные секунды; если сразу после пуша получили 404, повторите через полминуты.

## 3. Релиз в основном репозитории

```bash
./publish-step2-release.sh
```

Сначала проверяет, что CDN отвечает `200` и что коммит этой сборки уже на GitHub, затем создаёт тег
`@@TAG@@` и релиз в `@@MAIN_REPO@@` с описанием из `@@NOTES_FILE@@` и ассетами:

@@ASSET_TABLE@@

Хотите сначала посмотреть глазами — добавьте `--draft` в вызов `gh release create` внутри скрипта:
`releases/latest` останется на прежнем релизе, пока вы не нажмёте Publish вручную.

## 4. Проверка после публикации

```bash
curl -sI https://github.com/@@MAIN_REPO@@/releases/latest/download/update-manifest.txt | head -1
curl -s @@BASE_URL@@/updater.properties
```

Первая команда должна вернуть `HTTP/2 302` (редирект на файл), вторая — содержимое файла, а не
страницу с ошибкой. Полная проверка — на реальной установке: `WorldPainter-Update.exe --check-only`;
код `0` означает «всё актуально», `1` — «есть обновления», `2` — ошибка.

## Важно: сначала исходники, потом тег

`gh release create` вырезает тег из того коммита, на который сейчас смотрит ветка по умолчанию в
`@@MAIN_REPO@@`. Поэтому шаг 3 сам сверяет локальный `HEAD` с `HEAD` на GitHub и отказывается
публиковать, пока они разошлись: иначе «Source code (zip)» у релиза @@VERSION@@ оказался бы архивом
старого кода. Манифест и бинарники при этом были бы правильные — именно поэтому такую подмену легко
не заметить. Тег создаётся с `--target` на тот же самый коммит.

Если скрипт сказал, что исходники не совпадают — запушьте их и запустите шаг 3 заново:

```bash
git -C @@SRC_DIR@@ push origin HEAD
```

## Что где лежит

| Файл или папка | Куда идёт |

| `release-assets/` | ассеты релиза; шаг 3 передаёт их сам |

| `publish-step2-release.sh` | шаг 3 |
